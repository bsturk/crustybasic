# crustyBASIC on Commodore 64

Use `@OPTION TARGET c64` for the default C64 profile, or pick an
exact system with `@OPTION SYSTEM`.

Portable runtime calls are documented in [`../API.md`](../API.md).
This page covers C64 systems, modes, formats, and hardware notes. For
command-line target selection and dialects, see
[`../USAGE.md`](../USAGE.md).

## Systems

| System | Default output | Notes |
| --- | --- | --- |
| `c64.orig` | `.prg` | Default. Original NMOS C64 profile. |
| `c64.c64c` | `.prg` | C64C profile. Same feature set here. |
| `c64.sx64` | `.prg` | SX-64 portable profile with a built in disk drive and display. |
| `c64.ultimate` | `.prg` | C64 Ultimate profile with turbo, UCI, and REU support. |

## Outputs

Default `.prg` builds use the resident BASIC V2 ROM for `REAL` by
default and when optimizing for size. Speed builds use crustyBASIC's
built-in `REAL` support, as do cartridge builds.

Normal PRG and disk builds use `$0810-$9FFF` and `$C000-$CFFF`, skipping
BASIC ROM. Code and data can span both regions. The heap stays within
a single region.

Select `@OPTION NOBASIC TRUE` or `--set nobasic=true` to expose the
extra 8 KB at `$A000-$BFFF`, joining program RAM through `$CFFF`.
This works with PRG and disk output and uses built-in math and number
printing. KERNAL I/O remains available. BASIC ROM is restored when the
program ends. The included runtime routines reduce the net memory gain.

## Basics

The `cbm_basic_v2` dialect uses `SYS address`. Set A, X, Y, and status
with `POKE 780` through `POKE 783` before the call. Read the returned
values with `PEEK` at those addresses.

`SYS address, value, ...` works for machine code that reads its
arguments from the BASIC line, as most hires and sound libraries do. The
values are written as text behind a comma and CHRGET is pointed at that
text before the call, so the routine parses them exactly as it would in
a BASIC program.

| Item | Value |
| --- | --- |
| CPU | 6510, 6502 family |
| Text | 40x25 |
| Code start | `$0810` for `.prg`, `$8000` for cart |
| Program RAM top | `$D000` |
| Text screen | `SCREEN_BASE` (`$0400`) |
| Color RAM | `COLOR_BASE` (`$D800`) |
| String encoding | PETSCII |
| Main chips | VIC-II and SID |
| Recursive PROCs | Yes |

`.prg` files load with the normal Commodore `LOAD`, then start with
`SYS`.

## VIC-II Graphics

`DISPLAY_HIDE` hides the display without clearing it. `DISPLAY_SHOW`
reveals the current contents. `DISPLAY_VISIBILITY_SUPPORTED` is `TRUE`.
The border stays visible, including while using DISPLAY_MIXED.

The `VIC` namespace exposes common VIC-II registers. Use runtime
graphics and sprite calls first; use `VIC.*` when you need direct
hardware control.

`SCREEN_BASE` is the normal KERNAL text screen. `COLOR_BASE` is color RAM.
`VICII_SCREEN_BASE` is separate because it follows `@OPTION VICII_BANK` for
bitmap graphics and relocated video data.

`SPRITE_DATA` targets the active display. Bitmap modes use eight
shape slots in the graphics bank; the kernal text screen uses four
slots in the tape and RS-232 buffer area at `$02C0`-`$03FF`, so up to
four shapes are live over text and sprite ids sharing `id AND 3`
share a slot. Avoid text mode sprites while tape or RS-232 is in use.

Common names:

| Name | Purpose |
| --- | --- |
| `VIC.BORDER` | Border color. |
| `VIC.BACKGROUND`, `VIC.BACKGROUND1`..`3` | Background colors. |
| `VIC.RASTER` | Raster line. |
| `VIC.CTRL1`, `VIC.CTRL2` | Screen control and scroll bits. |
| `VIC.MEMORY` | Screen, bitmap, and character memory selection. |
| `VIC.SPRITE_ENABLE` | Enable sprite bits. |
| `VIC.SPRITE0_X`, `VIC.SPRITE0_Y` | Sprite 0 position. Sprite 1..7 match. |
| `VIC.SPRITE_X_MSB` | High X bits for all sprites. |
| `VIC.SPRITE_PRIORITY` | Sprite priority bits. |
| `VIC.SPRITE_MULTICOLOR` | Sprite multicolor enable bits. |
| `VIC.SPRITE_SPRITE_COLLISION` | Sprite collision latch, cleared on read. |
| `VIC.SPRITE_BG_COLLISION` | Sprite/background collision latch, cleared on read. |

```basic
VIC.BORDER = 0
VIC.BACKGROUND = 6
VIC.SPRITE_ENABLE = 1
VIC.SPRITE0_X = 100
VIC.SPRITE0_Y = 100
```

C64 graphics support standard, multicolor, and extended background color
text, plus hires and multicolor bitmaps. The default graphics mode is
`BITMAP_HIRES`.

| Mode | C64 mode | Size | Colors |
| --- | --- | --- | --- |
| `CELL` | VIC-II 40 column text | 40x25 | text |
| `BITMAP_HIRES` | VIC-II hi res bitmap | 320x200 | 2 |
| `BITMAP_LORES` | not supported | | |
| `BITMAP_MULTICOLOR` | VIC-II multicolor bitmap | 160x200 | 4 |
| `CELL_MULTICOLOR` | VIC-II multicolor text | 40x25 | 4 |
| `VICII_TEXT_ECM` | VIC-II extended background color text | 40x25 | 2 per cell |

Bitmap colors are shared by cells. Hires cells cover 8x8 pixels and have
one foreground and one background color. Multicolor cells cover 4x8 logical
pixels and have four color slots. `PLOT`, lines, shapes, and bitmap text set
the current `COLOR` on every cell they touch. Existing pixels that use a
changed slot also change color. A multicolor cell already using four distinct
colors cannot display a fifth color without replacing one of them.

`CELL_MULTICOLOR` uses one shared background, two shared multicolor
slots, and one foreground color per cell. `CELL_COLORS fg, bg, color2,
color3` sets those colors. Each cell's foreground uses C64 colors
0 through 7 because color RAM bit 3 selects multicolor rendering.

`DISPLAY VICII_TEXT_ECM` selects extended background color text on the C64.
Each cell has one foreground color from the full 16 color palette and one
of four shared backgrounds. Set them with `BACKGROUND_COLOR index, color`,
using indices `0` through `3`. `BACKGROUND_COLOR color` sets background `0`.
Use `CELL_COLOR` for the foreground and `CELL_PUTC` for the screen code:
bits 0 through 5 select glyph 0 through 63, and bits 6 and 7 select
background 0 through 3. This applies to both ROM and custom charsets.
`DISPLAY_HAS_MODE(VICII_TEXT_ECM)` returns true, and
`DISPLAY_MODE_COLOR_COUNT(VICII_TEXT_ECM)` returns 2 colors per cell.

`@OPTION VICII_BANK` selects a fixed 16 KB video bank by number:

| Value | Video bank | Bitmap | Screen attributes |
| --- | --- | --- | --- |
| `0` | `$0000-$3FFF` | `$2000` | `$0400` |
| `1` | `$4000-$7FFF` | `$6000` | `$4400` |
| `2` | `$8000-$BFFF` | `$A000` | `$8400` |
| `3` | `$C000-$FFFF` | `$E000` | `$C400` |

Bank 1 is the default. In bank 2 the bitmap sits under the BASIC ROM, which
stays mapped; the drawing calls page it out only while reading a pixel, so
`PEEK` of the bitmap area returns ROM bytes.

`DISPLAY_MIXED(mode, text_first_row, text_rows)` is available in VIC-II
banks 1 and 2 for hires and multicolor bitmap modes. It places one
full width text region anywhere in the 40x25 text grid. Cell calls use the
same absolute rows. `POSITION` and `PRINT` also write to the mixed text
region. Passing `0` for `text_rows` selects the same full screen mode as
`DISPLAY(mode)`, and a later `DISPLAY` call leaves mixed mode.
Passing `0, 25` for the text region shows steady full screen text without
raster switching. The bitmap is preserved; select a smaller text region
to show it again. Use `CELL_CLS` to clear the text cells.
The provider owns the C64 IRQ vector while mixed mode is active and polls the
normal CIA clock tick itself. It restores the previous IRQ vector and CIA
timer IRQ when `DISPLAY` leaves mixed mode.

## Scrolling

The portable SCROLL API supports horizontal and vertical cell scrolling on
the C64. Start an active axis with an 8 pixel step:

```basic
SCROLL_BEGIN U8(8), U8(8)
```

A zero step disables that axis. Horizontal scrolling uses a 40 column backing
surface with 38 visible columns. Vertical scrolling uses a 25 row backing
surface with 24 visible rows. VIC fine offsets handle the movement between
character boundaries. At each boundary, fill the requested edge with
`SCROLL_CELL_PUTC` or `SCROLL_CELL_COLUMN`, then call `SCROLL_PRESENT`.

`@OPTION SCROLL_DOUBLE_BUFFER` chooses the full screen method:

| Setting | Behavior |
| --- | --- |
| `FALSE` | One screen, with 80 bytes of row storage. Selected by default and size builds. Works in VIC-II banks 0 to 3. |
| `TRUE` | Two screens, with an extra 1 KB screen matrix. Default for speed builds. Works in VIC-II banks 0 to 2. |

An explicit setting overrides the build default. One screen is updated row
by row after the VIC has fetched each row, with interrupts paused during
the copy. A cell crossing can take more than one frame. Two screens allow
the next position to be prepared off screen and shown at a frame boundary;
use this setting when interrupt timing matters, such as background music.

Scrolling moves character codes with shared colors. Set them with
`CELL_COLORS` before scrolling; `SCROLL_CELL_COLOR_SUPPORTED` is `FALSE`.

`SCROLL_PRESENT` waits for a safe frame boundary. It does not install or
replace the public `FRAME_INSTALL` callback. Start from `DISPLAY CELL`.

`SCROLL_BEGIN_REGION` scrolls a band of rows sideways while the rows above
and below it stay still, in VIC-II banks 0 to 2. It uses its own two buffers,
regardless of `SCROLL_DOUBLE_BUFFER`:

```basic
SCROLL_BEGIN_REGION 0, 2, 40, 20, 8, 0
```

The band always spans the full width and does not scroll vertically. It is
shown from two spare screen matrices that a raster interrupt switches in at
the top of the band and out at its bottom, so the fixed rows keep their
cells, colors and the program's charset. The switch happens in the last
raster line of the row above the band and of the band's last row; keep the
cells at the right edge of those two rows blank to avoid a flicker there.
The band is copied a column sideways over the frames between two cell
crossings, half its rows per frame, so moves of up to 4 pixels a frame
keep an even frame cost; faster moves copy the whole band on the crossing
frame. Hardware sprites work over the band. Their pointers are copied into the
band matrices every frame, so write them as usual with `SPRITE_DATA` or
`VICII_SPRITE_POINTER`, and move sprites right after `SCROLL_PRESENT`
returns so the writes land before the beam reaches them.

`VICII_SCROLL_REGION_DISPLAY mode, charset` gives the band its own display
mode (`CELL`, `CELL_MULTICOLOR` or `VICII_TEXT_ECM`) and 2K aligned charset
inside the video bank, while the fixed rows keep the program's. Call it
before or after `SCROLL_BEGIN_REGION`. The provider owns the C64 IRQ vector
while a band scrolls and polls the CIA clock tick itself, like mixed mode,
so kernal keyboard input pauses; read keys with `KEY_HELD` or use the
joystick. `SCROLL_BEGIN` or the end of the program hands the vector back.

## Images

Native image display supports:

| Format | Accepted files |
| --- | --- |
| `IMAGE_FMT_C64_MULTI` | Koala Painter, 10003 bytes, load address `$6000`, including `$FE` RLE variants |
| `IMAGE_FMT_C64_HIRES` | Art Studio, 9002-9009 bytes, load address `$2000` |

At build time, `cb-image` and `@INCLUDE_IMAGE` also accept untiled 40x25
CharPad CTM9 bitmap projects in hires and multicolor modes.

Prepared Koala and Art Studio images use RLE automatically when it makes
the stored image smaller. This applies to embedded images and `.img` files.

Set `@OPTION IMAGE_USE_LZ TRUE` to pack prepared images with LZ instead of
RLE. LZ images are usually much smaller, so they load from disk faster and
take less memory, and they unpack faster than RLE images. Unpacking takes a
little more code. A program with this option unpacks only LZ and unpacked
images, so make its `.img` files with `@INCLUDE_IMAGE` or `cb-image --lz`.

```basic
@OPTION IMAGE_USE_LZ TRUE
@INCLUDE_IMAGE TITLE "title.png" FILE "TITLE.IMG"

OK = IMAGE_LOAD(TITLE_IMAGE_FILE)
```

Image effects work on unpacked Koala and Art Studio images. Wipes and
slides copy 8 pixel bands or cell columns. Fades step every colour cell
through a 4 step chain to black, so `IMAGE_FADE_STEPS` is `4`. Koala fades
include the background colour and Art Studio fades include the border.
`IMAGE_FADE_OUT` works on any bitmap screen, including images loaded from
disk. An unpacked Koala image takes 10013 bytes, so pick a `VICII_BANK`
with room for it below the bitmap.

`IMAGE_DISSOLVE_IN` and `IMAGE_DISSOLVE_OUT` reveal or erase scattered
pixels. Multicolor pixels stay intact. Dissolve out keeps the palette:
Koala pixels erase to the background color, and hires pixels erase to
each cell's background color. Dissolve in copies the image's palette
before revealing its pixels. The optional final block size is 1, 2, 4,
or 8 native pixels per side; multicolor pixels are twice as wide as hires pixels.

KERNAL-backed runtime image loading is available. A full Koala image
plus program code can exceed the default bitmap bank's code ceiling;
select `@OPTION VICII_BANK 3` for large programs.

`GFX_PRINT` and `GFX_PRINT_CENTER_X` draw bitmap text over an image without
mixed mode. Their last argument selects whether the background is transparent.

```basic
OK = DISPLAY(BITMAP_MULTICOLOR)
OK = IMAGE_LOAD("PICTURE.KLA")
COLOR WHITE, BLACK
GFX_PRINT 60, 184, "HELLO", TRUE
```

`FALSE` draws the background color over blank font pixels. `TRUE` does not
erase those pixels, but it is not a separate overlay layer. Drawing the font
pixels still applies the current `COLOR` to their shared bitmap cells, so
other image pixels using the same slots can change color.

Stop the raster around blocking disk access to keep the display stable. The
installed split is preserved and restarts without clearing either screen.

```basic
OK = DISPLAY_MIXED(BITMAP_MULTICOLOR, 22, 3)
RASTER_STOP
OK = IMAGE_LOAD("PICTURE.KLA")
RASTER_START
```

To show a loading message, use full screen text during disk access:

```basic
OK = DISPLAY_MIXED(BITMAP_MULTICOLOR, 0, 25)
CELL_CLS
POSITION 9, 12
PRINT "LOADING... PLEASE WAIT";
OK = IMAGE_LOAD("PICTURE.KLA")
IF OK THEN
    OK = DISPLAY_MIXED(BITMAP_MULTICOLOR, 22, 3)
ENDIF
```

## Charset and Tiles

### Runtime support

The C64 target supports 8 byte writable text glyphs in VIC-II character
memory. `CHARSET_COPY_DEFAULT` copies the ROM glyphs of the character set
in use into a writable charset and activates it. `CHARSET_RESET` returns
to that ROM set.
`CHARSET_INSTALL src_addr` copies and activates a complete 2048 byte
charset.

The target chooses a writable charset page and text screen in the bank
selected by `VICII_BANK`. Cell backed `TILE_DEFINE` installs a RAM
charset once, copies the ROM character shapes first, then writes defined
tile glyphs into that charset. Passing a base to
`TILE_BEGIN span_w, span_h, base` selects another 2K aligned charset
page.

### Asset imports

The build time charset and charmap importers accept CharPad CTM versions 7
and 9, including projects saved by CharPad Free 2.86. The C64 also declares
`ctm_c64` for CTM9 `@INCLUDE_TILESET` and
`@INCLUDE_TILEMAP`. It packs the project character pictures as 8x8 base tiles
and expands the CharPad tile layout into a base tile map.

The C64 also accepts indexed PNGs through `png_mono_8x8`, using the same
tileset and tilemap interface.

Hires, multicolor and extended background character modes are supported
with per project or per character colors. Charset data can be read from a
tiled project. A direct charmap requires the tile system to be disabled,
while tileset and tilemap imports require it to be enabled and stay in hires
or multicolor mode. Per tile colors are not supported yet.

In an extended background project the four background colors arrive as
`BACKGROUND` and `SHARED_COLOR_1` through `SHARED_COLOR_3`, ready for
`VIC.BACKGROUND` through `VIC.BACKGROUND3`, and every charmap cell keeps its
background choice in bits 6 and 7 of the character number. A `.cbm` map can
carry the same choice in its `attributes` list; shift an attribute left by
six and OR it into the tile ID when copying the map.

Imported charset data keeps the C64 hires or multicolor layout. Each entry in
the generated `*_COLORS` array includes the multicolor flag when needed, and
`*_PROPERTIES` contains the CharPad material value.

## Sprites

### Runtime support

The C64 has 8 hardware sprites. `SPRITE_DEFAULT_MODE` selects their reset
mode:

| `SPRITE_DEFAULT_MODE` | `SPRITE_WIDTH` x `SPRITE_HEIGHT` | Artwork row | Visible colors | Data |
| --- | --- | --- | --- | --- |
| `SPRITE_MODE_HIRES` (default) | 24x21 footprint | 24 one bit cells | 1 | 63 bytes |
| `SPRITE_MODE_MULTICOLOR` | 24x21 footprint | 12 two bit cells displayed double wide | 3 | 63 bytes |

`SPRITE_WIDTH` remains 24 because sprite coordinates and bounds use the
displayed footprint.

### Asset imports

The build time sprite importer accepts SpritePad 1.8.1 headerless files,
SpritePad version 5 files, and non-interlaced 8 bit indexed PNG files. Version
5 animation ranges are imported when present. Version 1.8.1 and PNG files have
no animation table, so programs choose their own frame ranges.

PNG sheets must be a multiple of 24x21 pixels. Frames are read from left to
right, then top to bottom. Each frame may use one visible color after PNG
transparency and `TRANSPARENT_COLOR` are applied.

Imported frames keep the native 24x21 size and 63 byte data layout. Expansion
and overlay values are kept as metadata, but multi sprite overlay drawing is
not provided yet.

### Sprite behavior

`SPRITE_INVERT_SUPPORTED` is `TRUE`. `SPRITE_INVERT` inverts the 63 bytes loaded
into a sprite slot. `SPRITE_EXPAND` can display a sprite at 48x42.
Both modes keep per sprite X and Y expansion, priority, and collision
latches.

`SPRITE_DATA` copies the same 63 target native bytes in either mode. It
does not convert a standard shape into a multicolor shape.

Each multicolor pixel uses one bit pair:

| Bits | Color |
| --- | --- |
| `00` | transparent |
| `01` | shared `SPRITE_COLOR2`, `VIC.SPRITE_MULTICOLOR0`, `$D025` |
| `10` | `SPRITE_COLOR`, `VIC.SPRITE0_COLOR` through `SPRITE7_COLOR`, `$D027` through `$D02E` |
| `11` | shared `SPRITE_COLOR3`, `VIC.SPRITE_MULTICOLOR1`, `$D026` |

`SPRITE_MODE id, mode` changes one sprite without changing the others. Direct
`VIC.SPRITE_MULTICOLOR` bits remain available.
`VICII_SPRITE_MULTICOLOR_COLORS c1, c2` sets the two shared colors.

`SPRITE_SHAPE_SLOTS` is 32. `SPRITE_SHAPE_INSTALL slot, addr` copies a 63 byte
shape to `VICII_SPRITE_SHAPE_BASE + slot * 64`, the first 2K of the bank's
bitmap area, and `SPRITE_SHAPE_SELECT id, slot` points a sprite at it by
writing `VICII_SPRITE_SHAPE_PTR0 + slot` into the bank's screen. Select the
bank first with `SPRITES_ON`, a charset call or `SCROLL_BEGIN_REGION`. The
slots share memory with the hires bitmap, so use them with text displays.

## SID Sound

Each SID has three voices. Sound uses native SID frequency values. Note
conversion uses MIDI-style note numbers.

Target-specific helpers are available through the `SID.*` namespace:

| Call | Purpose |
| --- | --- |
| `SID.FREQ VOICE, FREQ` | Set native 16-bit frequency. |
| `SID.ADSR VOICE, A, D, S, R` | Set envelope nibbles. |
| `SID.CTRL VOICE, CTRL` | Set waveform and gate bits. |
| `SID.PULSE_WIDTH VOICE, PW` | Set 12-bit pulse width. |
| `SID.GATE_ON VOICE`, `SID.GATE_OFF VOICE` | Toggle the gate bit. |
| `SID.FILTER CUTOFF, RES, VOICES, MODE` | Configure the filter. |
| `SID.MASTER_VOLUME VOLUME` | Set master volume. |
| `SID.OFF VOICE`, `SID.ALL_OFF` | Silence one voice or all voices. |

Useful constants include `TRIANGLE`, `SAW`, `PULSE`,
`NOISE`, `GATE`, and `VOLUME_MAX`.

`SID_CHIPS` accepts 1, 2, 4, or 8, providing 3, 6, 12, or 24 voices.
On the stock profiles the first N default bases follow the VICE order:
`$D400`, `$DE00`, `$DF00`, `$DF80`, `$DE80`, `$DF40`, `$DE40`, and `$DFC0`.
The `c64.ultimate` profile keeps all eight chips inside the SID area so the
REU and the command interface at `$DF00-$DF1F` stay free: `$D400`, `$D420`,
`$D480`, `$D4A0`, `$D500`, `$D520`, `$D580`, and `$D5A0`, matching its
`SID1` to `SID8` register namespaces. Use `SID.SET_BASE` to override a base
for other hardware:

```basic
@OPTION SYSTEM c64.orig
@OPTION SID_CHIPS 4
SID.SET_BASE 2, $D420
```

## Audio

The C64 plays prepared PSID tunes through the portable AUDIO API. By
default it uses frame service playback:

- `AUDIO_PLAYBACK_MODEL = AUDIO_PLAYBACK_FRAME_SERVICE` - each completed
  `FRAME_WAIT` invokes the tune's play address once.
- Tunes are embedded with `@INCLUDE_AUDIO`.
- `AUDIO_SOUND_SHARED = FALSE` - AUDIO owns the SID while active.
  `AUDIO_STOP` silences every SID register; PSID has no general
  deinitializer.

```basic
@INCLUDE_AUDIO TUNE "assets/tune.sid"

OK = AUDIO_LOAD(ADDR TUNE_AUDIO)
OK = AUDIO_PLAY

WHILE RUNNING
	FRAME_WAIT
ENDWHILE
```

Audio plays automatically during BASIC work and serial disk reads,
including `IMAGE_LOAD`, `FILE_LOAD`, and `TEXT_LOAD`.
`AUDIO_PLAYBACK_MODEL` is `AUDIO_PLAYBACK_AUTOMATIC`.
`AUDIO_STOP` and `AUDIO_UNLOAD` stop music. Audio, `@PERIODIC IRQ`
callbacks, display splits, and scrolling share the display interrupt.
`@PERIODIC IRQ` runs once per display refresh, independently of
`FRAME_WAIT`. An optional number sets the minimum interval in milliseconds.

Playback uses 254 bytes of player scratch storage plus interrupt state
and code. Some tunes need over 12,000 extra CPU cycles per player call,
which slows foreground work and loading. Serial reads let interrupts run
while waiting for the drive; the KERNAL briefly masks them while receiving
each byte. Operations that mask interrupts can delay audio and callbacks.

The accepted PSID subset is strict: versions 2-4 with built-in player
data, one SID chip, a nonzero play address, VBlank speed for every song,
a clock matching the resolved `REGION` (or both), init and play entry
points inside the loaded payload, and the whole payload inside
`$0400-$9FFF`. RSID, MUS/PlaySID files, CIA-speed songs, multi-SID
files, and self-installed interrupt players are rejected at compile
time. Public song `N` maps to initializer value `N - 1`; the no-argument
`AUDIO_PLAY` uses the tune's start song.

A PSID payload contains executable 6510 code and is trusted content:
the header cannot prove its code avoids undeclared zero page or RAM.
The compiler treats its declared payload range like the fixed range of
any included asset. If the default program code would overlap it, the
code moves above the payload automatically. A fixed program placement
or a payload that leaves no room is still a compile error. `AUDIO_LOAD`
copies the payload to its load address and `AUDIO_PLAY` recopies that
pristine source before every start, so stop and replay never reread any
medium, and self-modifying tunes restart cleanly. Every init and play
call runs with the caller's `$01` banking saved, the standard `$37`
mapping selected, and the PAL/NTSC indicator at `$02A6` set from
`REGION`.

## Input

| Capability | Value |
| --- | --- |
| Keyboard | Yes |
| Individual held keys | Yes |
| Joystick ports | 2 |
| Buttons | 1 per port |
| Stick type | Digital |
| Paddle axes | 4 |
| Keypad ports | 0 |
| Keypad `INPUT` | No |
| Mouse buttons | 0 |

Paddle reads use SID `POTX`/`POTY`. Trigger reads follow the native
active-low convention: `0` means pressed, `1` means released.

`KEY_HELD(code)` scans the keyboard matrix without consuming typed input.
It supports `KEY_SPACE`, `KEY_0` through `KEY_9`, and `KEY_A` through
`KEY_Z`.

`RAWKEY` and `RAWKEY_CODE` read held keys directly, including during mixed
display. They support Shift, Commodore, and Control without consuming
buffered text input.

## Timing

The runtime tick source is the KERNAL jiffy clock. It runs at about
60 Hz on PAL and NTSC because the KERNAL calibrates the CIA timer by
video standard. The 24-hour wrap is compensated for one crossing.

The CBM clock calls are specific to this target family:

| Call | Purpose |
| --- | --- |
| `TI` | Read the 24 bit KERNAL jiffy clock as `U32`. |
| `TI_SET jiffies` | Set the KERNAL jiffy clock from the low 24 bits. |
| `TI$` | Return the clock as a six character `HHMMSS` string. |

`TICKS` uses `TI` as its source. `TICKS_RESET` records a new starting
value without changing the KERNAL clock.

## Extended memory

`EXTMEM_SUPPORTED` and `CBM_REU_SUPPORTED` are `TRUE` because the target
implements the portable extra-memory interface with REU DMA. This does not
mean an REU is attached. `EXTMEM_AVAILABLE()` probes the hardware at runtime.
Portable programs should use the `EXTMEM_*` interface. `EXTMEM_FILL` and
`EXTMEM_VERIFY` use the REU's hardware fill and comparison paths.
`EXTMEM_REU` is the explicit handle for the same provider.

### REU image

`EXTMEM_IMAGE_SUPPORTED` is `TRUE`. Assets included with `EXTMEM` go into an
REU image written beside the program with a `.reu` extension. Fetch them with
the `EXTMEM_REU` handle:

```basic
@INCLUDE_FILE LEVELS "levels.bin" EXTMEM

EXTMEM_FETCH EXTMEM_REU, LEVELS_LEN, ADDR LEVELS, LEVELS_XADDR, LEVELS_BANK
```

The image is 512 KB unless `@OPTION EXTMEM_IMAGE_KB` picks 128, 256, 1024,
2048, 4096, 8192, or 16384. VICE only loads an image that matches its REU
size:

```
x64sc -reu -reuimage hello.reu hello.d64
```

Add `-reusize n` when `EXTMEM_IMAGE_KB` is not 512. On an Ultimate, load the
`.reu` file into the REU before starting the program.

## SX-64

Select the portable SX-64 system with:

```basic
@OPTION SYSTEM c64.sx64
```

The SX-64 has the same C64 memory map, VIC-II, SID, BASIC ROM, and KERNAL
jump table used by crustyBASIC, so it supports the same `.prg`, disk, and
cartridge outputs as `c64.orig`.

The machine adds a built in device 8 disk drive and 5 inch display. It has no
cassette or RF port. Its KERNAL disables tape access, makes disk the default
for loading and saving, changes `Shift` + `Run/Stop` to load and run from disk,
and uses higher contrast startup colors. The portable file API already defaults
to disk device 8 on every C64 profile.

The SX-64 user port is not electrically identical to the C64 user port: one
9 VAC line is grounded instead of floating. Check SX-64 compatibility before
connecting C64 user port hardware.

## C64 Ultimate

Use an exact C64 Ultimate system when you want the Ultimate specific
hardware APIs:

```basic
@OPTION SYSTEM c64.ultimate
```

This enables UCI support automatically. A stock C64 fitted with a 1541
Ultimate-II+ cartridge can enable the same support explicitly:

```basic
@OPTION C64_ULTIMATE_SUPPORTED TRUE
```

The option selects the provider at compile time. `UCI_AVAILABLE()` checks the
UCI identification register at runtime, so it returns `0` when the cartridge
is missing or its command interface is disabled. `FILES_AVAILABLE()` and
`NET_AVAILABLE()` use the same runtime check.

The C64 Ultimate profile adds:

| API | Purpose |
| --- | --- |
| `SPEED_DETECT`, `SPEED_TURBO`, `SPEED_NORMAL`, `SPEED_SET` | Software controlled turbo. Index 15 is 48 MHz on the C64 Ultimate profile. |
| `UCI_AVAILABLE()` | Ultimate Command Interface availability. |
| `FILES_*` | Fast file access through the UCI DOS target. |
| `NET_*` | TCP and UDP access through the UCI network target. |

The Ultimate's built-in REU uses the same portable `EXTMEM_*` interface.
The address is `BANK` plus a 16-bit offset, so bank 255 reaches the 16 MB
range.

## Text

`TEXT_ENCODING` tells the compiler which screen character set your text
is written for. It selects the string bytes without changing the screen
character set or forcing letters to uppercase or lowercase.

| Setting | Intended screen character set | Source `A-Z` | Source `a-z` |
| --- | --- | --- | --- |
| `UPPER_CASE` (default) | Uppercase and graphics (`{UPPER}`) | `$41-$5A` | `$61-$7A` |
| `MIXED_CASE` | Lowercase and uppercase (`{LOWER}`) | `$C1-$DA` | `$41-$5A` |

The default suits the uppercase and graphics character set selected at
C64 power on. Write uppercase source text for letters; lowercase source
characters encode graphics. A newline becomes `$0D` in either encoding.

Startup leaves the current character set alone. Printing `{LOWER}` or
`CHR(14)` selects mixed case; printing `{UPPER}` or `CHR(142)` selects
uppercase and graphics. These controls change the whole screen, including
text already printed. Returning to BASIC keeps that selection.

The brace escapes are names for control bytes. `CHR` creates a string
containing the byte; the screen acts on it when it is printed.
`PRINT "{LOWER}";` and `PRINT CHR(14);` therefore do the same thing.
Assigning `S$ = CHR(14)` only stores the control byte; `PRINT S$;` selects
the character set.

`LOWER(S$)` and `UPPER(S$)` return a copy with the letters converted using
the selected encoding. They leave the screen character set unchanged.

The encoding and screen character set must match to display the intended
letters. With `UPPER_CASE`, source `A` becomes byte 65, which the
C64 displays as `A` in uppercase and graphics mode but `a` in mixed case
mode. With `MIXED_CASE`, source `A` becomes byte 193 and source `a`
becomes byte 65, preserving both cases when `{LOWER}` is active.
Thus `PRINT "{LOWER}HELLO"` displays `hello` with the default encoding
and `HELLO` with `MIXED_CASE`.

For source text with both letter cases, select the encoding and screen
character set explicitly:

```basic
@OPTION TARGET c64
@OPTION TEXT_ENCODING MIXED_CASE
PRINT "{LOWER}HELLO, WORLD!"
PRINT "Free memory: ", HEAP_AVAIL
PRINT "Done."
```

The encoding applies to the whole program. Controls such as `{UPPER}`
change the display, not the bytes of later literals or stored strings.
Mixed case strings can therefore show graphics after `{UPPER}`.

`CHR(205)`, `{$CD}`, and `{205}` supply the exact same PETSCII byte in
either encoding. With the uppercase and graphics character set, bytes
205 and 206 draw the two diagonal lines. Named controls also keep their
exact bytes. The CBM BASIC dialect keeps the VICE petcat listing convention,
including `~` for `$FF`.

Common escapes:

| Escape | Byte |
| --- | --- |
| `{RETURN}`, `{ENTER}` | `$0D` |
| `{TAB}` | Four spaces |
| `{CLEAR}`, `{CLR}` | `$93` |
| `{HOME}` | `$13` |
| `{LOWER}`, `{TEXT_LOWER}` | `$0E` |
| `{UPPER}`, `{TEXT_UPPER}`, `{GRAPHICS}` | `$8E` |
| `{LEFT}`, `{RIGHT}`, `{UP}`, `{DOWN}` | Cursor controls |
| `{RVS_ON}`, `{RVS_OFF}` | Reverse video controls |

## Files

`FILE_LOAD_PROGRAM(path$)` loads a PRG from disk device 8 using its
stored address. `FILE_LOAD_PROGRAM(path$, dst)` uses `dst` instead.
Both skip the two address bytes and load the remaining file through
KERNAL LOAD. They return zero on success or the KERNAL error code,
without running the loaded code.

File channels run from 1 to 15. `FILE_OPEN` uses disk device 8, and the
KERNAL allows up to 10 files open at once.
`FILE_OPEN_NATIVE` can choose another device or secondary address.

Use the two-path `@INCLUDE_FILE` form to stage exact runtime bytes:

```basic
@INCLUDE_FILE TITLE "TITLE.KLA" "assets/TITLE.KLA"
OK = IMAGE_LOAD(TITLE_FILE)
```

Building with `@OPTION OUTPUT_TYPE disk` or `--set output-type=disk`
writes both the assembled `.prg` and a `.d64` containing that program.
Staged asset files are also added to the D64.

A 1541 directory holds 16 characters, so files staged by a two-path
`@INCLUDE_*` form come out uppercase and trimmed to fit. A runtime name of
`"title.kla"` gives `TITLE.KLA` on the disk and in the generated constant.

The D64 wrapper also looks for a companion directory beside the source
named `<program>.disk_files`. Regular files inside it are copied into the
generated disk image as `SEQ` files using their leaf filenames.

The lower KERNAL channel helpers are also callable by target-specific
programs: `OPEN_CH`, `CLOSE_CH`, `GET_CH`, `PUT_CH`, `PRINT_CH_STR`,
`ST`, and `CMD_CH`.

## Raster

`DISPLAY_MIXED` starts raster switching when text and bitmap share the screen.
`RASTER_STOP` leaves
the VIC-II in the full bitmap mode while preserving that program.
`RASTER_START` resumes it, and `RASTER_UNINSTALL` removes it. With all 25 rows
selected as text, `RASTER_STOP` and `RASTER_START` keep steady text mode.
Frame waits poll the VIC raster line.

## Cartridges

Select cartridge output at build time with `--set output-type=cart`:

```text
crustybasic build <input.cbs> --set output-type=cart -o program.crt
```

Use source-level `OUTPUT_TYPE` only when the program should always build
as a cart:

```basic
@OPTION TARGET c64
@OPTION OUTPUT_TYPE cart
```

Default carts use standard 8K/16K `.crt` output. For larger programs,
select the Super Games mapper:

```basic
@OPTION TARGET c64
@OPTION OUTPUT_TYPE cart
@OPTION MAPPER supergames
```

`supergames` provides four switched 8K banks plus a fixed 8K area.
See [`../USAGE.md#banked-builds`](../USAGE.md#banked-builds) for
`@BANK`.

For EasyFlash output, select `cart-easy-flash`:

```text
crustybasic build <input.cbs> --set output-type=cart-easy-flash -o program.crt
```

```basic
@OPTION TARGET c64
@OPTION OUTPUT_TYPE cart-easy-flash
```

`cart-easy-flash` uses EasyFlash 16K banks. Main code is placed in
physical bank 0. Use `@BANK 0` through `@BANK 62` for switched
banks; those are emitted as physical banks 1 through 63. Switched bank
code cannot call `MAIN`.

## Dialects

`cbm_basic_v2` and `cbm_basic_v7_0` use Commodore suffix rules: bare
numeric names, `!`, and `#` are `REAL`, `%` is 16-bit integer, and `$`
is `STRING`. Use `cbm_basic_v3_5` for Plus/4 BASIC 3.5 listings.

In Commodore BASIC dialects, `RND(X)` returns a `REAL` fraction from
`0` up to, but not including, `1`. Use `RAND(N)` for portable bounded
integers.
